# Anatomy of a Good Repository: Marine Science Edition

A well-structured repository is the foundation of reproducible science. It ensures that your field data, processing scripts, and figures can be easily understood and re-run by your future self, journal reviewers, or research collaborators.

---

## Repository Schematic 

```text
marine-science-project-repo/
│
├── .git/                                   # 🔒 HIDDEN SYSTEM FOLDER: Leave completely alone
│
│
├── .github/                                # ⚠️ SYSTEM CONFIG FOLDER: Do not modify or touch
│   └── workflows/                          # Automated background tasks (e.g., rendering website)
│
│
├── data/                                   # Project data split by status
│   ├── raw/                                # Raw field data/instrument readouts (Read-only, never modify!)
│   └── processed/                          # Cleaned, derived, or subsetted data generated by scripts
│
│
├── docs/                                   # Supplemental info (Field logs, cruise reports, protocol PDFs)
│
│
├── figures/                                # Plots, maps, and visualizations generated by scripts
│
│
├── scripts/                                
│   ├── 01_data_cleaning.R                  # Code files for analysis and data cleaning
│   ├── 02_spatial_mapping.R                # Numbered sequentially to show workflow order
│   └── 03_statistical_models.R
│
│
├── .gitignore                              # Tells Git which files to ignore (e.g., massive raw datasets)
├── environment.yml / requirements.txt      # Project dependencies (software & library versions)
├── LICENSE                                 # Legal terms for how others can use your code/data
└── README.md                               # The main introductory page for your project
```

## 📄 The Anatomy: Essential Files & Folders Explained

### 1. `.git/` (🔒 The Time Machine — Leave Completely Alone)
This is a hidden directory that Git creates automatically when you initialize a repository (`git init`). It acts as the "brain" and time machine of your project.
* **What it does:** It stores your entire version control history, tracking every change you commit, your branches, and your links to GitHub. If you delete or alter this folder, your project will lose its entire history and stop being a Git repository.
* **What you should do:** Leave it completely alone. In fact, it is hidden by default on most operating systems specifically so you don't accidentally modify its contents.

### 2. `data/` (Your Research Foundation)
To preserve the integrity of your science, data is strictly separated into two states:
* **`data/raw/`:** This is your holy grail. Once your instrument readouts (e.g., CTD casts, acoustic data, Niskin bottle logs) are saved here, they should never be touched or edited manually. 
* **`data/processed/`:** Any dataset that has been cleaned, filtered for outliers, or merged by a script belongs here.

### 3. `scripts/` (The Analytical Pipeline)
Instead of keeping a disorganized pile of code files, your analysis files live entirely inside this folder. They should be written programmatically so they read from `data/raw/` and output clean files into `data/processed/` or plots into `figures/`.

### 4. `.github/` (⚠️ System Automation — Do Not Touch)
Similar to the `.git/` folder, this directory is used by GitHub to run backend automations (like GitHub Actions). For example, it might contain workflows that automatically check your code for syntax errors, test your packages, or host a project website. **Unless you are updating the automation logic itself, do not modify, rename, or delete files in this folder.**

### 5. `environment.yml` or `requirements.txt` (Dependencies)
Code ages, and software updates can change how functions work. This file explicitly documents the precise programming language version (e.g., R 4.3 or Python 3.11) and the exact versions of the packages/libraries you used (like `ggplot2`, `sf`, or `spatial`). Documenting your dependencies ensures that someone else can replicate your exact computing environment five years from now without your code throwing errors.

### 6. `LICENSE` (The Sharing Rules)
Without a license file, your repository defaults to exclusive copyright, meaning others cannot legally use, adapt, or cite your code. In scientific research, permissive open-source licenses are preferred:
* **MIT License:** Perfect if you want to share your scripts broadly. Anyone can use and adapt your code as long as they attribute it to you.
* **CC-BY 4.0 (Creative Commons):** Ideal if your repo primarily shares open data, making it easy for other scientists to reuse your data while requiring them to cite your work.
* **NOAA:** NOAA has a specific liscence for github repositories and sharing government work. 

### 7. `.gitignore` (The Size Filter)
Oceanographic data—like satellite NetCDF files, sonar bathymetry grids, or underwater high-definition video—is often gigabytes in size. **Git is not built to track massive data files.** Use your `.gitignore` file to tell Git to ignore your `data/raw/` folder or specific file types (like `.csv` or `.nc`). This keeps your GitHub repository lightweight and fast, tracking your *code*, while your massive datasets remain safely stored on institutional servers or dedicated repositories like Zenodo. 

***.gitignore can ignore any file***, this means that you can use this file to ignore passwords, pdfs, environment files, etc...

## 📁 Fundamentals of Good Repo Organization

### 1. The Raw Data is Sacred
Never click into an Excel spreadsheet in `data/raw/` to manually fix a typo or remove an empty row. Doing so breaks the reproducibility trail. Any data fixing or filtering out of bad sensor readouts must happen transparently inside a script in your `scripts/` folder.

### 2. Number Your Scripts Chronologically
Avoid names like `analysis_final_v2.R`. Instead, prefix your scripts with numbers (e.g., `01_load_and_clean.R`, `02_spatial_mapping.R`). This shows a reviewer exactly how data flows from raw measurements to final paper figures.

### 3. Use Relative Paths
Never use absolute file paths in your scripts (such as `read.csv("C:/Users/YourName/Documents/MarineProject/data/raw.csv")`). If you move the folder or share it with a collaborator, the path breaks instantly. Always use paths relative to the project root directory (e.g., `../data/raw/buoy_data.csv`).
